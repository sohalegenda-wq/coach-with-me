# Продолжение установки со старой profiles

Эта инструкция относится к обнаруженной старой таблице:

| Столбец | Тип |
| --- | --- |
| id | uuid |
| username | text |
| display_name | text |
| license | text |
| created_at | timestamp with time zone |

Она несовместима с обычной новой установкой: `CREATE TABLE profiles` выдаёт `42P07`, а сайту нужны `nickname`, `bio`, `club`, `avatar` и `banned`.

## Что запустить

1. Откройте в GitHub **supabase/upgrade-legacy-profiles.sql** → Raw.
2. Скопируйте весь файл.
3. В Supabase → SQL Editor → New query вставьте его и нажмите Run.

Это полный файл продолжения установки: добавляет нужные поля, остальные таблицы, RLS, процедуры проверки и учебное наполнение. Не запускайте дополнительно обычный `setup-sql-editor.sql`, исходные миграции или `legacy-profile-compat.sql`.

После успеха должны появиться `courses = 5`, `lessons = 19`, `exam_questions = 115` и число `preserved_profiles` — сколько старых профилей сохранено в закрытой копии.

## Что сохраняется

Все исходные строки и значения `id`, `username`, `display_name`, `license`, `created_at` сохраняются. В `nickname` копируется отображаемое имя (до 60 символов; полное остаётся в `display_name`), а если имени нет — username. Даже старые имена пользователя, не соответствующие новым правилам регистрации, остаются прежними.

До изменений создаётся закрытая копия `private.cwm_legacy_profiles_backup`. Политики, права, ограничения и заменённые триггеры сохраняются в `private.cwm_legacy_setup_backup`. Клиентские роли не могут читать эти таблицы.

Старое поле `license` остаётся историческим. Его значения **не превращаются автоматически в сертификаты**: они могли задаваться старым интерфейсом без официального экзамена. Если ранее выданная лицензия подтверждена, администратор может перенести её через административную панель с причиной. Новые аккаунты не наследуют старое значение по умолчанию.

Аккаунты Auth, существующие без профиля, получают недостающий профиль с незанятым именем `legacy_N`. Все получают обычную роль student; права администратора из старой таблицы/metadata не переносятся.

## Безопасность и совместимость

Скрипт заменяет старые политики profiles на доступ владельца/администратора и убирает старые клиентские права записи, включая права на отдельные столбцы. RLS остаётся включён.

Распознаваемый Auth-триггер, который только создавал профиль, заменяется на новый: два триггера одновременно могли бы сломать регистрацию. Неоднозначные триггеры с дополнительными действиями, собственные триггеры profiles, другая структура и конфликтующие уже установленные таблицы вызывают остановку. Вся установка находится в одной транзакции: при ошибке изменения откатываются.

Запуск однократный. Повторное выполнение останавливается без удаления уже установленных данных. При сообщении о несовместимости пришлите полный текст ошибки, не удаляйте таблицы и не отключайте RLS.

## После установки

Настройте переменные сборки Cloudflare, Auth redirect URLs, SMTP и разверните две Edge Functions по [основной инструкции](CONNECT-SUPABASE.md). SQL сам не публикует функции и не изменяет настройки Cloudflare.

Зарегистрируйте/откройте аккаунт, проверьте профиль и сохранение черновика урока. Администратора назначает владелец через SQL Editor, как описано в основной инструкции.

## Для разработчиков

Файл сгенерирован командой `npm run db:legacy` из канонических миграций и `supabase/legacy-profile-compat.sql`. Канонические миграции для чистой установки не изменяются.

Проверки на одноразовой локальной БД:

```bash
CWM_TEST_LEGACY=1 npm run test:db
node scripts/build-legacy-upgrade.mjs --check
```

Проверяются сохранность данных и закрытой копии, старые политики/права, конфликтующие Auth-триггеры и откат, регистрация, повторный запуск и полный цикл урока/экзамена/лицензии. Тестовый скрипт, как и обычные DB-тесты, удаляет схемы только в одноразовом PostgreSQL на localhost:55432; к рабочему Supabase его не подключают.
