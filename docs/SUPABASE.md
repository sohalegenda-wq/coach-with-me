# Подключение Supabase

## 1. Проект и публичная конфигурация

Создайте проект на Supabase Free или используйте существующий. Скопируйте **Project URL** и **Publishable key** (или legacy `anon`). В текущей среде переданные пользователем URL и публичный ключ записаны только в игнорируемый `.env.local`.

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_PUBLIC_PUBLISHABLE_KEY
```

Используйте корневой адрес, без `/rest/v1/`. `VITE_*` попадает в браузер; там разрешены только эти публичные значения. `service_role`, пароль PostgreSQL, AI API keys и access token Supabase в них не размещают.

## 2. Примените SQL

Перед применением к существующему проекту проверьте, что таблицы не конфликтуют с другими приложениями; используйте отдельный проект для академии. Миграции предназначены для однократного применения к чистой схеме приложения и не удаляют чужие таблицы.

**Через SQL Editor** (без CLI):

1. Откройте `supabase/migrations/202610230001_academy.sql`, скопируйте весь файл в SQL Editor проекта и выполните.
2. Выполните `supabase/migrations/202610230002_content.sql`.
3. Проверьте: 5 курсов, 19 уроков, 115 вопросов; у таблиц включён RLS, схема `private` не входит в Exposed schemas Data API.

**Или через CLI** (нужен Docker только для локальной разработки, не для `db push`):

```bash
npx supabase@2.121.0 login
npx supabase@2.121.0 link --project-ref YOUR_PROJECT_REF
npx supabase@2.121.0 db push
```

Входите в CLI самостоятельно и вводите секреты через защищённый интерфейс/менеджер секретов, не в чат. CLI управляет версионированием миграций. Не смешивайте SQL Editor и `db push` без согласования истории миграций (`supabase migration repair`). Повторное выполнение исходных миграций не требуется. Для последующих изменений создавайте новую миграцию, не перегенерируйте применённую.

Аккаунты хранятся в `auth.users` — это штатная таблица `users` Supabase Auth, не отдельная небезопасная копия паролей. Триггер создаёт `profiles` и роль `student`. Аккаунтам Auth, существовавшим до миграции, создаются профили с уникальными именами `legacy_1`, `legacy_2` и т. д.; никнейм можно изменить в профиле. Уникальность email контролирует Auth, username — ограничение БД. Пароли обрабатывает только Auth.

## 3. Auth

В Authentication:

- Включите Email provider и регистрацию.
- Оставьте подтверждение email включённым.
- Минимум пароля: 10 символов (также проверяется интерфейсом).
- URL Configuration → Site URL: `https://YOUR_SITE.pages.dev`.
- Redirect URLs: `https://YOUR_SITE.pages.dev` и `https://YOUR_SITE.pages.dev/**`; при своём домене добавьте его, для разработки — `http://localhost:5173/**`.
- Настройте SMTP через Authentication → Email / SMTP. Выберите поставщика с подходящей бесплатной квотой. Тестовый отправитель Supabase ограничен и не подходит для неограниченной публичной регистрации.
- При необходимости настройте CAPTCHA и email rate limits в Supabase. Если включаете обязательную CAPTCHA, сначала добавьте её виджет и передачу токена в Auth UI отдельной задачей; текущая форма рассчитана на стандартную Email-конфигурацию без CAPTCHA.

PKCE сохраняет контекст входа в браузере. Ссылку подтверждения/восстановления открывайте в том же браузере, где инициировали запрос. После подтверждения тренер может входить с любого устройства по email и паролю. Смена пароля в профиле проверяет текущий пароль; восстановление — через письмо.

Сессия сохраняется Supabase SDK, access token обновляется автоматически. Локальное хранилище содержит сессию, а не учебную базу; профили, черновики и результаты всегда в PostgreSQL.

## 4. Разверните Edge Functions

Создайте локально файл вне Git, например `/tmp/cwm-functions.env`:

```dotenv
ALLOWED_ORIGINS=https://YOUR_SITE.pages.dev,http://localhost:5173
AI_PROVIDER=disabled
AI_MODEL=gpt-4o-mini
```

Добавьте основной домен, если он отличается. Origins указываются без завершающего `/`, через запятую. Не используйте `*` для продакшена. Для preview-веток явно добавляйте нужный origin.

```bash
npx supabase@2.121.0 secrets set --env-file /tmp/cwm-functions.env
npx supabase@2.121.0 functions deploy academy-api
npx supabase@2.121.0 functions deploy coach
```

`SUPABASE_URL` и `SUPABASE_ANON_KEY` доступны функциям автоматически. Service-role key не нужен: функции используют JWT тренера, а PostgreSQL проверяет `auth.uid()` и роль.

В `supabase/config.toml` для функций стоит `verify_jwt=false`: это отключает только проверку шлюзом с устаревшим JWT-секретом. Обе функции **сами проверяют Bearer token через `auth.getUser`** перед любой операцией. Это совместимо с publishable keys и асимметричными ключами Auth. Не удаляйте ручную проверку из `_shared/http.ts`.

## 5. Первый администратор

1. Зарегистрируйте аккаунт обычным способом, подтвердите email.
2. Найдите UUID пользователя в Authentication → Users.
3. В SQL Editor выполните, заменив UUID:

```sql
update public.app_roles
set role = 'admin'
where user_id = 'YOUR_USER_UUID'::uuid;
```

4. Выйдите и снова войдите. Появится пункт «Администратор».

Никнейм, metadata, URL страницы и данные из браузера не выдают права. Роли меняются только доверенным владельцем БД. Для проверки экзаменов администратора нужен второй администратор — сервер запрещает самопроверку.

## 6. ИИ — по желанию

Без ИИ оставьте `AI_PROVIDER=disabled`. Основные функции не зависят от провайдера.

Поддержаны API формата OpenAI Chat Completions:

| AI_PROVIDER | Адрес на сервере | Пример модели (уточните доступность у провайдера) |
| --- | --- | --- |
| `openai` | `https://api.openai.com/v1` | `gpt-4o-mini` |
| `groq` | `https://api.groq.com/openai/v1` | выберите доступную Chat Completions модель |
| `openrouter` | `https://openrouter.ai/api/v1` | выберите доступную модель с бесплатной квотой |
| `compatible` | `AI_BASE_URL` (HTTPS) | модель вашего совместимого API |

В Supabase → Edge Function Secrets задайте `AI_API_KEY`, `AI_PROVIDER`, `AI_MODEL`; `AI_BASE_URL` нужен только для `compatible`. Эти значения не задаются в Cloudflare Pages и не попадают в Git. Не отправляйте их в чат. Для локального секретного файла используйте права только владельцу (`chmod 600`) и удалите после настройки.

В админ-панели включите ИИ и установите дневной лимит (0–50 запросов на пользователя; по умолчанию 15). Лимит считается атомарно в БД, в том числе для неуспешных вызовов. Системный контекст строится сервером из текущего прогресса, лицензий и последних 8 сообщений. Сообщения — недоверенные данные. Наставник не имеет инструментов изменения баллов или лицензий.

Timeout 20 секунд, максимум ответа ограничен. Недоступность, ошибка 429 или пустой ответ переключают интерфейс на явно подписанный учебный режим. Это не даёт провайдеру право автоматически списывать деньги — лимиты расходов задайте у него отдельно.

## 7. Финальная проверка

- Создайте два обычных аккаунта, проверьте уникальность username/email и подтверждение писем.
- Под первым аккаунтом сохраните урок, войдите в другом браузере — должен появиться тот же черновик.
- Второму аккаунту не должны быть видны чужие ответы/профиль/результаты.
- Завершите курс D, начните экзамен, сохраните, возобновите и отправьте 20 ответов + 3 текста от 80 слов.
- До ручной проверки лицензии нет. Администратор оценивает 12 критериев, сервер суммирует результат; при ≥70 появляется лицензия и сертификат в профиле.
- Проверьте disabled ИИ: наставник продолжает подготовленные упражнения, остальные части сайта работают.
- Разрешите только необходимые origins; не добавляйте схему `private` в Data API.

Если запрос возвращает `relation ... does not exist`, применены не все миграции. `Failed to send a request to the Edge Function` — проверьте deploy и `ALLOWED_ORIGINS`. `permission denied` — проверьте, что выполнена первая миграция полностью. Не отключайте RLS для устранения ошибок.
